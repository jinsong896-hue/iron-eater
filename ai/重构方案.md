# 《噬铁者》项目重构方案 —— 模块化与接口独立

> 2026-09-20 制定。基于当日代码实测（非旧文档），全部数据来自 grep/wc 实测。
> 本文档只做规划，**不含任何已实施的改动**。

---

## 〇、痛点与根因对照

| 症状 | 实测证据 | 根因 |
|---|---|---|
| 每次更新都牵连大量代码 | `player.gd` 2231 行 / **119 个函数**；改一个功能要在这一个文件里找上下文 | 上帝类：拾取/交互/状态机/特效/相机/音效/武器 7 类职责挤在 1 个文件 |
| 修 A 坏 B（回归反复出现） | PROGRESS 里 4 轮回归全出自这 4 个大文件 | 修改面 = 文件面积；小改动也在 2000 行的海洋里航行 |
| 同一件事多种写法 | GameRoot 查找有 **6 种写法**（组/向上走/`/root` 直取/`find_child`/特征属性/`current_scene`），HUD 因此吃过一个静默失效 bug | 无唯一真相源，每个新代码按当时心情挑一种 |
| 静默失效频发 | 门重入、音效两轮、屏幕震动、毒气 HUD——全是"不报错只是不生效" | 隐式耦合：节点查找、动态 `load()`、无人订阅的信号，失败时都返回 null/空而不报警 |
| 测试不敢动 | 23 套测试里 **110 处直呼 `._私有()` + 28 处 `.call("_...")`** | 测试直接钉住实现细节，重构 = 重写测试 = 失去保护网 |

**架构总评**：分层目录（core/data/gameplay/world/entities/rendering/ui）本身是健康的——
UI 零反向依赖 gameplay、data 层纯净，这两条底线守住了。问题不在"层"，在"块"：
每层内部都有几个把整层职责吃掉的大文件，加上跨层的隐式字符串耦合。

---

## 一、目标架构

### 1.1 依赖方向（不变，但补两条新规则）

```
UI (CanvasLayer)
  ↓ 只读
表现层 Player3D / Enemy3D / Room3D          ← 拆分主战场
  ↓ 显式接口
逻辑层 Combat / Skill / Loot / DungeonGen   ← 拆分次战场
  ↓
数据层（纯数据，零依赖）
核心层 EventBus / GameManager ← 拆分为职责单一的服务
```

**新规则 A —— 逻辑层不得 `load()` 表现层**：
现状 `room_controller.gd:733` 动态 `load("res://entities/enemies/boss_mechanics.gd")`，
`game_root.gd:498,520` 动态 load `hidden_wall.gd` / `special_prop.gd`。
改为**注册表反转**：表现层在启动时把工厂注册进逻辑层的 `SpawnRegistry`，
逻辑层按 key 取。加载失败时注册表报警，而不是返回 null 静默跳过。

**新规则 B —— 同一资源的查找只允许一种写法**：
GameRoot、当前房间、群体管理器各建唯一访问器（见 2.1），
其余 5 种写法全部删除。今后 grep 到旧写法即为 bug。

### 1.2 重构后的文件规模目标

| 文件 | 现在 | 目标 | 手段 |
|---|---|---|---|
| `entities/player/player.gd` | 2231 行 / 119 函数 | ≤ 400 行 | 拆 6 个组件 |
| `entities/enemies/enemy_base.gd` | 2174 行 | ≤ 500 行 | 拆 4 个组件 |
| `gameplay/dungeon/room_controller.gd` | 1633 行 | ≤ 400 行 | 拆 4 个控制器 |
| `scenes/game_root.gd` | 1110 行 | ≤ 400 行 | 拆 3 个服务 |
| 其余文件 | 全部 < 1000 行 | 不动 | —— |

**标准：单个文件 = 单个改动理由。** 改拾取逻辑只该打开拾取组件，
改门逻辑只该打开门控制器。这是"每次更新不再连坐"的直接判据。

## 二、基础设施（阶段 0，先行，零行为变化）

### 2.1 `core/service_locator.gd` —— 唯一查找入口

现状 6 种 GameRoot 查找写法散在 `player.gd` / `projectile_manager.gd` /
`room_controller.gd` / `hidden_wall.gd` / `minimap_view.gd` / `hud.gd`。

统一为一个静态类：

```gdscript
class_name GameRef
extends RefCounted
## 唯一的跨层引用入口。所有"找 GameRoot / 找当前房间 / 找群体管理器"
## 一律走这里，别处再出现同类查找即为违规。
static func game_root() -> Node          # 组优先 + 特征属性兜底，带缓存
static func current_room() -> Node       # 经 GameRoot.current_room_node（引用，不受 SubViewport 边界影响）
static func crowd_manager() -> Node      # 经当前房间的 RoomController
static func pickup_field() -> Node       # 懒创建语义记录在案（null = 正常态）
static func player() -> Node3D           # 组优先
```

**验收**：全项目 grep 旧写法，除 `GameRef` 内部外零命中；
门禁 23 套全绿。这一步直接消灭本项目已两次咬人的 bug 类
（HUD 毒气那次 + player 拾取那次虚惊）。

### 2.2 `tests/helpers/` —— 测试访问集中层

138 处私有成员直呼是最大的重构风险。不要求一次性消除，先**收口**：

- 新建 `tests/helpers/probe.gd`：把 `.call("_spawn_crowd_at")`、`p._hitstop()` 之类
  全部封装成命名函数（`probe.spawn_crowd_at(ctrl, ...)`）。
- 测试文件只 import helper，不再直接摸下划线成员。
- **重构时改 helper 一个文件**，测试语义零变化。

**验收**：`grep -c '\.call("_' tests/*.gd` 归零；门禁全绿且断言数不变。

### 2.3 静默失效报警器

针对本项目最高频的 bug 类（不报错只是不生效），在 `core/` 加一个
`WiredCheck` 静态工具，供启动/切房时自查：

- 关键信号表：`EventBus` 每个信号标注"谁发、谁收"，`WiredCheck` 在
  debug 构建启动时打印**有发无收**的清单（11 个死信号一次列出，留档）。
- 关键节点表：`SpawnRegistry` / `GameRef` 找不到目标时
  `push_warning`（现状全部静默返回 null）。

这不是行为改动，是把"静默"变"有声"，今后同类缺陷在第一分钟暴露。

## 三、阶段 1：拆 `player.gd`（2231 → 6 组件）

**拆分依据是实测的职责块**（括号为关键词出现次数）：

| 新文件 | 搬出内容 | 对外接口（唯一入口） |
|---|---|---|
| `entities/player/pickup_component.gd` | 拾取 34 处：`_pickup_field` / `_nearest_pickup` / `_pickup_nearby` / PICKUP_RANGE | `try_pickup()` |
| `entities/player/interact_component.gd` | 交互 13 处：`_unhandled_input` 的 E 键三段分流、隐藏墙/特殊房交互 | `try_interact()` |
| `entities/player/combat_component.gd` | 挥砍 43 处中的几何与命中：`_hit_enemies_in_cone` / `_apply_pierce_line_at` / `_apply_hit_crowd` | `hit_cone()` / `hit_line()` |
| `entities/player/fx_component.gd` | 视觉反馈：`_screen_shake` / `_flash` / `_slash_visual` / 挥砍 mesh | `play_hit_fx()` 等 |
| `entities/player/audio_component.gd` | 5 处 `AudioManager.play` 调用 + 触发时机 | `play(name)` |
| `entities/player/stats_facade.gd` | 15 处 `GameManager.attributes` + 11 处 `stat_value` 的读法收口 | `stat(n)` / `eff_atk()` |

**`player.gd` 保留**：CharacterBody3D 生命周期、移动物理、状态机接线
（states/ 目录已是独立文件，不动）、组件装配与转发。

**关键约束**：
- 组件间**不互相引用**，需要协作的一律经 player 转发或走 EventBus——
  否则只是把大文件改成大网。
- `take_damage` / `die` / `cast_skill` 等 35 个公开 API **签名不变**
  （外部 17 处调用点零改动）。
- 每搬完一个组件：`bash tests/run_all.sh` 必须全绿才搬下一个。

## 五、阶段 3：拆 `room_controller.gd`（1633 → 4 控制器）

实测职责块：特殊房 72 / 门 54 / 刷怪 48 / 群体 44。

| 新文件 | 搬出内容 | 备注 |
|---|---|---|
| `gameplay/dungeon/spawn_director.gd` | 刷怪 48 处：`_spawn_points` 收集、白名单、节点/群体分流 | **同时消灭对 entities 的反向依赖**（见规则 A） |
| `gameplay/dungeon/door_manager.gd` | 门 54 处：锁门/解锁/重入保护/disarm | 与 `doors_by_topology.gd` 合并成一处门真相 |
| `gameplay/dungeon/special_room_controller.gd` | 特殊房 72 处：商店/赌徒/附魔/记忆碎片 | `special_room_service.gd`（413 行）本就是它的数据层，合并归位 |
| 群体接线 44 处 | 留在 `crowd_manager.gd`（669 行，已独立） | 只把 `room_controller` 里的转接代码搬过去 |

**反向依赖的解法（规则 A 落地）**：

```gdscript
# core/spawn_registry.gd
## 表现层启动时注册工厂；逻辑层按 key 取。
## 注册缺失 → push_warning（不再静默刷 0 怪）
static func register(key: String, factory: Callable) -> void
static func spawn(key: String, parent: Node, data: Dictionary) -> Node
```

`enemy_base.gd` / `boss_mechanics.gd` 在 `_ready` 或项目启动时注册自己；
`spawn_director` 只认 key。**收益**：逻辑层从此可以脱离表现层单测
（现在 `room_controller` 单测必须拉起整个敌人场景）。

## 七、阶段 5：`GameManager` 瘦身与 `EventBus` 契约化

### GameManager（203 行但职责面极宽）

拆成职责单一的服务，GameManager 退化为门面（外部 API 不变）：

| 新文件 | 内容 |
|---|---|
| `core/run_stats.gd` | kills / damage / gold / devour / fusion（纯数据 + 重置） |
| `core/phase_machine.gd` | GamePhase 状态机（4 个空钩子现属占位，收敛到一处） |
| `core/meta_progress.gd` | 钥匙碎片局内/局外双计数（存档读写已独立，归位） |

### EventBus 契约化

- 每个信号上方注释固化**发射者 ↔ 订阅者**清单（谁发谁收一行说清）。
- 11 个有发无收的信号：**保留但加 `## 无人订阅（预留扩展面）` 标注**，
  删除与否是你已挂账的决策项（PROGRESS 第二十节），本方案不替你定。
- 新增信号必须同时写清订阅方，否则 `WiredCheck` 启动时会点名。

## 八、执行纪律（防止"重构本身变成新债"）

1. **每阶段独立提交**，提交信息格式 `refactor(<域>): 拆出 <组件>（行为零变化）`。
2. **门禁是唯一验收**：每搬一个组件跑一次 `bash tests/run_all.sh`，
   23 套 + `PASSED` 字样双判据，红了就地修，不带病前进。
3. **不做顺手美化**：不改命名风格、不调目录结构、不动 addons/、
   不"顺便修 bug"（发现的 bug 单独记档单独修）。
4. **顺序有依赖**：阶段 0（GameRef + test helper）必须最先——
   它是后面所有阶段的地面；阶段 1/2 可并行；阶段 3 依赖阶段 0 的
   SpawnRegistry；阶段 4 依赖阶段 3 的 door_manager；阶段 5 随时可做。
5. **任何阶段可停在半路**：每个组件搬完即自洽，不存在"拆了一半的文件"
   （组件是新增文件，player.gd 每次删一段、每段独立成提交）。

## 九、验收清单（全部完成时）

- [ ] 6 种 GameRoot 查找 → 1 种（`GameRef`），grep 旧写法零命中
- [ ] `player.gd` ≤ 400 行；`enemy_base.gd` ≤ 500；`room_controller.gd` ≤ 400；`game_root.gd` ≤ 400
- [ ] 逻辑层对 `entities/` 的 `load()` 归零（走 SpawnRegistry）
- [ ] 测试文件对 `._私有` 直呼归零（全部经 `tests/helpers/probe.gd`）
- [ ] EventBus 30 信号全部有发射者/订阅者注释；死信号有显式标注
- [ ] `WiredCheck` 在 debug 启动时输出"有发无收"清单且可控静音
- [ ] 门禁 23 套全绿，断言总数不低于当前 1368
- [ ] 抽查验证"单一改动理由"：改拾取范围只动 pickup_component.gd；
      改门防抖只动 door_manager.gd

## 十、明确不做（本方案排除项）

- **不改目录结构**——现有分层是健康的，挪目录是纯扰动。
- **不引入新框架/模式**（不搞依赖注入容器、不搞 MVC/MVVM 重写）——
  GDScript 组合 + 注册表已够，引入重框架会制造新的学习成本。
- **不动 C++ 核接口**（crowd_sim / projectile_sim 的 FFI 契约）。
- **不处理 228 个零引用模型文件**（与模块化无关，另案）。
- **不碰 11 个死信号的存废**（用户已挂账的决策项）。
- **不重写测试**——只搬运访问方式（经 helper），断言语义一字不改。
