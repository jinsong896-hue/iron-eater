## 一、四条回归的排查结果

用户报告"着色器渲染实装后出现四条回归"。逐条实测定位，结论如下
（**不预设"都是着色器造成的"**，每条都以代码/实测为准）：

### ① 单位数量多时严重卡顿 —— 已修（真实断链）

**根因**：群体模拟（CrowdSim，2048 容量 + MultiMesh 渲染）整条路径是
**死代码**——`MonsterDB` 里没有任何条目带 `swarm` 标记，于是
`RoomController._should_use_crowd()` 恒返回 false，`CrowdManager`
从不被创建。

**修法**：`data/monsters/monster_db.gd` 增加 `SWARM_BASE_KEYS`
（`zombie` / `berserker` / `hound` 三个基础怪）+ `"swarm"` 派生键。

**验证**：门禁 `room_flow` / `framework` 等套件在启用 swarm 后仍全绿；
`RoomCombatLoop` 用例实测本房会真的刷出群体单位。

### ② 切换房间时严重卡顿 —— 已修（真实断链）

**根因**：`preload_all()`（逐帧预建后续房间，消除切房时的同步建造成本）
**零生产调用点**。

**修法**：在 `next_floor()`（层间切换，有整屏传送特效盖着）与
`generate_dungeon()`（`_cinematics_enabled()` 为真时）调用。
后者在无过渡遮罩的路径（测试直调/调试跳层）**提前 return**，
避免在无过渡的情况下同步卡住一帧。

### ③ 掉落物无法正常拾取 —— 已修（根因与着色器无关，是像素化管线的输入阻断）

**用户描述**：靠近掉落物按 E **毫无反应，连提示都没有**。

**排查**：按 E 若真的到达 `Player._unhandled_input`，`_pickup_nearby()`
**必然**发一条 message（找不到也发"附近没有可拾取的掉落物"）。
"连提示都没有" ⇒ 事件根本没到 Player。

**根因**：像素化提交 `24ec3978` 把 Player 从场景根直接子节点搬进了
`GameRoot/ViewportContainer/SubViewport`，而 `pixel_renderer.gd` 在该视口上
设了 `gui_disable_input = true` —— 这会让视口**完全不接收转发事件**。

移动/攻击走 `Input.is_action_pressed()` 轮询（全局 Input 单例，与视口无关），
所以照常工作；唯独交互键 E 走 `_unhandled_input`，被静默饿死。

**实测验证**（临时探针，已删）——在 SubViewport 内外各挂一个 `_unhandled_input`
探针，注入 E 键：

| `gui_disable_input` | `handle_input_locally` | 视口内收到事件 |
|---|---|---|
| **true（修复前）** | false | ❌ 收不到 |
| false | false | ✅ 收到 |
| true | true | ❌ 收不到 |
| false | true | ✅ 收到 |

`gui_disable_input` 是决定项，`handle_input_locally` 不影响事件**送达**
（它管的是"本视口是否消费事件"）。修复后探针实测
`EventBus.message: 附近没有可拾取的掉落物` 正常触发。

**修法**：`pixel_renderer.gd` 改为 `gui_disable_input = false`；
`scenes/main.tscn` 的 SubViewport 节点同步显式写 `gui_disable_input = false`
（否则改 tscn 的人会看到 `true` 而与代码矛盾）。

**"不让 3D 视口吃掉给 UI 的输入"这一诉求由 `handle_input_locally = false` 满足**，
与 `gui_disable_input` 无关。

### ④ 失败后回主页面 UI 按钮点不动 —— 已修

**排查结论**：主菜单 `main_menu.gd` 是**四个菜单里唯一没设**
`process_mode = PROCESS_MODE_ALWAYS` 的（pause / settlement / settings 都设了）。
`settlement_panel._on_continue()` 确实先 `paused = false` 再切场景，故常规
"死亡→结算→主菜单"不会带暂停进来——**但不能依赖这一条**：任何一条在
`paused == true` 时切到主菜单的路径都会让整个菜单冻结（按钮不响应，
ESC 也不响应）。

**修法**：`main_menu.gd` 的 `_ready()` 补上 `PROCESS_MODE_ALWAYS`，与另三个菜单对齐。

**补充核实**：`loading_screen.finish()` 的 `MOUSE_FILTER` 释放已经在 await 之前，
即历史上"载入遮罩挡住点击"的机制已不存在；主菜单场景内也没有 SubViewport，
不受 ③ 的输入阻断影响。

## 二、门禁自身的假阴性缺陷 —— 已修

**现象**：`bash tests/run_all.sh` 每轮报**不同的**套件失败（framework+floor_flow
→ proj_mgr+floor_flow → proj_mgr），而同样的套件单独跑却通过。

**根因**：套件跑完调 `get_tree().quit(0)`，进程随即退出，**stdout 管道里尚未
冲刷的缓冲被丢掉**——`$(...)` 抓到的流是**被截断的**，截断位置每次不同。
证据：某轮输出第 43 行刚打印 `ALL FLOOR FLOW TESTS PASSED`，第 44 行紧接着
`(未出现 PASSED 标记——脚本可能加载失败或挂起)`。

**修法**：`run_all.sh` 改为**退出码 + 文本标记双判据**（抽出共用 `_judge()`）。
退出码不受缓冲影响，是权威信号；文本标记保留，用于兜住"退出码 0 但实际有
断言失败"的情况。

**验证方式**（遵守"不得为验证工具而覆盖真实文件"）：另建两个临时探针脚本——
一个含故意语法错误（期望判 FAIL）、一个裸 `quit(0)` 且无 PASSED 标记
（期望判 PASS）。两者判定均正确，探针已删。

## 三、`proj_mgr` 间歇性失败 —— 已修（**测试缺陷，非产品 bug**）

**现象**：`test_projectile_manager.tscn` 约 4 次挂 3 次，报
`[FAIL] 投射物对群体单位造成伤害（hp 500 → 500）` 或
`[FAIL] 爆炸波及半径内的群体单位（hp 500 → 500）`。

**排查过程**（逐步排除）：核的 `get_position_buffer` 布局、`_is_crowd_ref` /
`_apply_damage_to_crowd` 守卫、阵营映射、`_sim_manager` 的 `found[0]` 取法
——全部正确。加逐帧诊断后拿到决定性数据：

```
[DIAG] f9  ref=4 crowd id=1 at (6.00,6.00)   # 刚生成，还在测试指定的坐标
[DIAG] f17 ref=4 crowd id=1 at (14.60,15.00) # 一帧内跳到别处
```

**根因**：测试把群体假人刷在**硬编码坐标** `(6,6)` / `(14,14)`，而模拟核每帧跑
`phase_collide_obstacles` —— 单位若落在**墙格**上会被立刻推出墙外（`(14,14)`
那次被推到 `(14.6,15.0)`，位移 0.6）。测试却仍按**生成坐标**发射投射物，
于是弹道从单位旁 0.6 米处擦过，恰好超出命中半径
（`rr = 目标半径 0.35 + 子弹半径 0.30 = 0.65`，只差 0.05 的余量）。
房间布局逐次随机 ⇒ 只有落在墙格的那些轮次失败。

**修法**：测试改为**按单位的实际位置**发射投射物
（`crowd.call("unit_position", id)`），并把落点从 `(6,6)`/`(14,14)`
（在多个房间 JSON 里都是墙）挪到房间内部的原点附近。

**验证**：连续跑 10 次，`pass=10 fail=0`；随后全量门禁连续 3 次 22/22。

## 七、群体单位 / 投射物换掉占位网格（任务清单第二条，本轮完成）

此前群体单位是 `CapsuleMesh`、投射物是 `SphereMesh`，都是占位。本轮改为
**billboard 精灵**，并顺带把两者的渲染统一到一支着色器上。

### 新增

| 文件 | 作用 |
|---|---|
| `rendering/shaders/unit_billboard.gdshader` | 群体单位与投射物**共用**的 MultiMesh 实例着色器 |
| `data/tiles/sprite_defs.gd` | 单位精灵表的唯一真相源（哪一格是哪种单位、按什么规则挑格） |
| `assets/sprites/units_16x16.png` | 烘焙产物：tiny-dungeon 图集底部四行 × 前 5 列（80×64，5 列 × 4 行） |

**为什么两支场景共用一支着色器**：billboard 数学（从实例矩阵取缩放、绕 Y 轴
朝相机、顶点存单位尺寸）**逐字相同**，差别只有两处——群体单位从
`INSTANCE_CUSTOM` 取精灵格采样图集，投射物不采样、颜色走 `COLOR`。
复制成两支会让这段数学有两份真相，而两边的缓冲布局本来就一样
（都恰好开一个实例通道 ⇒ stride 16）。用 `use_instance_color` 一个 bool 分流。

**弹丸不用贴图**：tiny-dungeon 的角色行里没有弹丸类小图，为子弹单独烤一张
1 格贴图不值得。配色复用既有的 `Projectile.element_color()`
（近战/旧投射物路径的唯一真相源），另起一套会立刻产生不一致。

**接触阴影做进着色器**而不是另开阴影实例：MultiMesh 每实例只有一条 transform
+ 一条通道，加阴影要么翻倍实例数、要么每帧在 GDScript 里重算 buffer
（2048 单位下这份开销就吃掉帧预算）。现在是精灵自身下半部按 `smoothstep`
压暗，给俯视相机一个"站在地上"的锚点。

### 踩坑一：MultiMesh 的实例步长（stride）与缓冲长度

**这是本轮最隐蔽的一处**，写下来免得重犯。

- 核产出的渲染缓冲是**每实例 12 个 float**（3×4 变换矩阵）——这是核的契约，
  C++ 侧与降级侧实现一致，不能改。
- 而 MultiMesh **开几个实例通道决定 stride**：只开 `TRANSFORM_3D` 是 12，
  再开**恰好一个**（`use_custom_data` 或 `use_colors`）是 **16**
  （12 变换 + 4 通道，通道落在 float [12..15]），两个都开是 20。
- `multimesh.buffer = <数组>` 是**整段赋值**，长度与 MultiMesh 现有缓冲不符时
  Godot **直接拒收**（`Cannot set a buffer on a Multimesh that is a different
  size from the Multimesh's existing buffer`），**表现是"单位一只都不显示"**
  ——不是报错崩溃，是静默不画。

所以两个管理器的 `_sync_render()` 都必须做一次 **12→16 的重排**，
不能把核的数组直接赋过去。

**这处还连带出了三条门禁失败**（`class_mech` 2 条 + `gameplay` 1 条）：
每帧一条错误日志拖慢了物理循环，恰好打破两个对帧数/计时敏感的用例
（冲刺双击、连击衰减）。排查时**没有预设"是既有 flaky"**——先把两个改动文件
`git stash` 掉跑门禁（22/22 全绿）证明是自己的改动引起，再 `git stash pop` 定位。

### 踩坑二：`use_custom_data` / `use_colors` 必须在 `instance_count` 之前设

设过 `instance_count` 之后再切这两个开关，Godot 报
`Instance count must be 0 to toggle whether custom data is used`。
两个 `_setup_multimesh()` 里的赋值顺序因此不能动，代码里已写注释标明。

### 踩坑三：精灵烘焙抠反了（**已修**）

第一版截图里每只怪都顶着一块**黑方块**。诊断过程：

1. 检查烘焙产物：`alpha 直方图 0:112 / 255:5008` ⇒ 98% 不透明，背景根本没抠掉。
2. 回头读**源图**：它是索引色 PNG（colorType=3），`tRNS` 只有 1 项且值为 0
   ⇒ **只有调色板索引 0 是透明的**，角色外的空白格用的正是索引 0。
3. 而当时被当成"背景色"的 RGB(118,59,54) 是调色板**索引 24**，
   那是角色的**深栗色描边**。

于是第一版按颜色距离抠图**正好抠反**：把描边抠成透明、把真背景留成不透明。
且因为黑方块在深色场景里不显眼，很晚才被发现。

**正确做法**：调色板索引 → RGBA 直接展开（alpha 取 `tRNS[i]` 或 255），
**不做任何颜色阈值判断**。重烘后不透明 3986 / 透明 1134（22.1% 透明），
剪影干净。教训已写进 `sprite_defs.gd` 文件头：
**索引色 PNG 先读 `tRNS` 和 PLTE，不要靠肉眼取色猜背景。**

### 验证

窗口化实跑（`--headless` 下 MultiMesh buffer 回读恒为空、`set_instance_transform`
被丢弃，**stride 问题只能在有窗口模式下复现**）：9–15 只群体单位渲染出三种
不同精灵（村民 / 橙衣壮汉 / 灰狼），7 发元素配色弹丸（火橙 / 冰蓝 / 电黄 /
毒绿 / 土棕 / 风白 / 无元素白）。临时探针与中间产物已全部清理。

## 八、待用户决策（本轮新增）

以下几项**已明确是设计/审美取向问题，不替用户拍板**：

1. **billboard 是否要朝向移动方向**。两侧核的渲染缓冲**都不写旋转**
   （只有对角缩放 + 末列位置），所以单位只能"永远正面朝相机"，无法"朝行进方向"。
   要支持得改 `crowd_sim.cpp` 的 `fill_render_buffer` **和** `crowd_sim_fallback.gd`
   **并重编 DLL**（本机未见 SCons 工具链）。
2. **美术风格落差**。tiny-dungeon 是明亮可爱的地牢包，《噬铁者》是暗色锈铁主题。
   是否调色/换源是审美决定。
3. **范围**：本轮只做了**群体单位 + 投射物**。玩家（`player.tscn` 的
   `CapsuleMesh_player`）与节点式敌人（`enemy_base.gd:_create_visual()` 的
   `CapsuleMesh`）**也还是胶囊**，换它们是大得多的改动（涉及动画状态、
   朝向、受击闪白等一整套表现）。
4. **群体单位动画**。素材每个角色只有**单帧**。要做多帧动画得走
   `custom_data` 传帧号 + `INSTANCE_CUSTOM` 在着色器里换格，
   核不需要改（通道数据本来就有 4 个 float 富余），但需要素材支持。

## 十一、群体路径词缀接入（任务清单第二条，本轮完成）

### 问题

词缀（`AffixDB`，怪物设计分册第 7 章）本来是挂在 `EnemyBase` 节点上的：
数值型由 `AffixDB.apply()` 写进 monster dict，非数值型由
`enemy_base._apply_affix()` 装配战斗钩子。

群体单位**不是场景节点**，两条路都断了。房间生成里 `AffixDB.apply()` 在
swarm/节点分流**之前**就跑了（`room_controller.gd:642`），所以群体单位
拿到了带 `affixes` 的 monster dict，但群体路径**只读了 `speed_pct`**
（生成时读一次），其余全部静默失效：

| 词缀 | 群体路径旧行为 |
| --- | --- |
| fast | 只有 `speed_pct` 泄漏进来，且**根本没写回核**（见下） |
| strong | `atk` 写进 dict 但从不读 |
| burn / freeze / revenge / immortal / lifesteal / void / chaos | 全部失效 |

### 实现

- **新增** `gameplay/enemies/crowd_affix_store.gd`（`CrowdAffixStore`）——
  按单位 id 索引的词缀状态与结算。数值口径逐条对齐 `enemy_base` 的同名常量。
- **新增** `CrowdManager.damage_unit(id, amount, attacker, pos)` ——
  所有"由 GDScript 侧发起的伤害"统一入口。复仇/不朽必须**在扣血之前**介入，
  直接 `apply_damage` 会让这两种词缀失效。调用方已全部迁移：
  `player._apply_hit_crowd`、`projectile_manager._apply_damage_to_crowd`、
  `projectile_manager._explode_crowd`。
- **新增** `CrowdManager._set_unit_speed(id, speed)` —— 核没有 `set_speed`，
  走 despawn + 同位 spawn（LIFO 保证 id 不变）。
- **新增** `CrowdUnitHost.take_damage(amount, is_crit, knockback, from)` ——
  群体单位的节点代理，承接玩家「伤害反弹」词条的回流伤害。
- **新增** `CrowdManager.host_of(id)` —— 暴露宿主节点（`buffs_of` 要穿
  `BuffHolder._target` 私有字段，语义不清）。
- `crowd_attacked` 信号**加 `id` 参数**，`room_controller._on_crowd_attacked`
  据此把攻击者节点补上。

### 过程中发现并修掉的四个真 bug

1. **`force_position` 不存在**。`_apply_on_hit_affixes` 调了
   `_player.call("force_position", ...)`，但全项目只有
   `enemy_base._swap_with_player` 里的 `has_method` 检查提到过这个名字，
   **从未定义**。后果：词缀·虚空把怪瞬移走了、玩家留在原地。
   改为直接写 `global_position`（与 `_swap_with_player` 的 else 分支一致）。

2. **反伤调用签名错**。`note_damage` 用四参
   `attacker.call("take_damage", back, null)`，但生产路径上 `attacker`
   **永远是玩家**，玩家侧是两参 `take_damage(amount, from)`。
   Godot 报 `Cannot convert argument 2 from Nil` 并**静默反伤失败**——
   `enemy_base._reflect_to` 的注释里记着同一个坑。已改两参。

3. **`_atk_interval` 被复位覆盖**。`_apply_spawn_affixes` 里先写
   `_atk_interval` 再调 `_recompute_attack_params()`，而后者在
   `active <= 0` 时会**复位成默认 1.2**。由于该函数在 `active += 1`
   之前调用，**第一个单位生成时必然被覆盖**——表现为"攻击间隔永远是
   默认值，怪物的 `attack_interval` 不生效"。已把写入挪到重算之后。

4. **`fast` 词缀在群体路径上从未生效**。`speed_pct` 只被 `_spawn_crowd_at`
   读去当 spawn 参数，而词缀生效需要**再乘一次**；且核里 `speed` 只在
   spawn 时能写，故必须在交给核之前算好。现在 `spawn_unit` 在 spawn 后
   立刻用 `_set_unit_speed` 写回调整过的速度。

### 有意的范围收缩（非遗漏）

- **混沌**只改移速：核里 `attack_range/interval/damage` 是**全体共用**的
  一组参数，改不了单个单位（节点侧会随机改攻速/移速/攻击力三项）。
  为补偿，群体侧**每次都改移速**，把节点侧三分之一的频率补回来。
  重掷是**围绕生成倍率**做的（不是原地累乘），否则倍率会随时长漂走。
- **燃烧/冰冻**复用玩家侧既有的 `BuffHolder` 词条（`burn` / `frost`），
  与节点侧 `enemy_base` 施加的是同一套。
- **精英标记仍未透传给核**（`sim.set_elite` 从未被调），
  `crowd_died` 的 `is_elite` 恒为 false。影响面小（`_should_use_crowd`
  已把精英挡在群体路径外），故未动。
