## 一、四条回归的排查结果

用户报告"着色器渲染实装后出现四条回归"。逐条实测定位，结论如下
（**不预设"都是着色器造成的"**，每条都以代码/实测为准）：

### ① 单位数量多时严重卡顿 —— 已修（真实断链）

**根因**：群体模拟（CrowdSim，2048 容量 + MultiMesh 渲染）整条路径是
**死代码**——`MonsterDB` 里没有任何条目带 `swarm` 标记，于是
`RoomController._should_use_crowd()` 恒返回 false，`CrowdManager`
从不被创建。

**修法**：`data/monsters/monster_db.gd` 增加 `SWARM_BASE_KEYS`
（`zombie` / `berserker` / `hound` 三个基础怪）+ `"swarm"` 派生键。

**验证**：门禁 `room_flow` / `framework` 等套件在启用 swarm 后仍全绿；
`RoomCombatLoop` 用例实测本房会真的刷出群体单位。

### ② 切换房间时严重卡顿 —— 已修（真实断链）

**根因**：`preload_all()`（逐帧预建后续房间，消除切房时的同步建造成本）
**零生产调用点**。

**修法**：在 `next_floor()`（层间切换，有整屏传送特效盖着）与
`generate_dungeon()`（`_cinematics_enabled()` 为真时）调用。
后者在无过渡遮罩的路径（测试直调/调试跳层）**提前 return**，
避免在无过渡的情况下同步卡住一帧。

### ③ 掉落物无法正常拾取 —— 已修（根因与着色器无关，是像素化管线的输入阻断）

**用户描述**：靠近掉落物按 E **毫无反应，连提示都没有**。

**排查**：按 E 若真的到达 `Player._unhandled_input`，`_pickup_nearby()`
**必然**发一条 message（找不到也发"附近没有可拾取的掉落物"）。
"连提示都没有" ⇒ 事件根本没到 Player。

**根因**：像素化提交 `24ec3978` 把 Player 从场景根直接子节点搬进了
`GameRoot/ViewportContainer/SubViewport`，而 `pixel_renderer.gd` 在该视口上
设了 `gui_disable_input = true` —— 这会让视口**完全不接收转发事件**。

移动/攻击走 `Input.is_action_pressed()` 轮询（全局 Input 单例，与视口无关），
所以照常工作；唯独交互键 E 走 `_unhandled_input`，被静默饿死。

**实测验证**（临时探针，已删）——在 SubViewport 内外各挂一个 `_unhandled_input`
探针，注入 E 键：

| `gui_disable_input` | `handle_input_locally` | 视口内收到事件 |
|---|---|---|
| **true（修复前）** | false | ❌ 收不到 |
| false | false | ✅ 收到 |
| true | true | ❌ 收不到 |
| false | true | ✅ 收到 |

`gui_disable_input` 是决定项，`handle_input_locally` 不影响事件**送达**
（它管的是"本视口是否消费事件"）。修复后探针实测
`EventBus.message: 附近没有可拾取的掉落物` 正常触发。

**修法**：`pixel_renderer.gd` 改为 `gui_disable_input = false`；
`scenes/main.tscn` 的 SubViewport 节点同步显式写 `gui_disable_input = false`
（否则改 tscn 的人会看到 `true` 而与代码矛盾）。

**"不让 3D 视口吃掉给 UI 的输入"这一诉求由 `handle_input_locally = false` 满足**，
与 `gui_disable_input` 无关。

### ④ 失败后回主页面 UI 按钮点不动 —— 已修

**排查结论**：主菜单 `main_menu.gd` 是**四个菜单里唯一没设**
`process_mode = PROCESS_MODE_ALWAYS` 的（pause / settlement / settings 都设了）。
`settlement_panel._on_continue()` 确实先 `paused = false` 再切场景，故常规
"死亡→结算→主菜单"不会带暂停进来——**但不能依赖这一条**：任何一条在
`paused == true` 时切到主菜单的路径都会让整个菜单冻结（按钮不响应，
ESC 也不响应）。

**修法**：`main_menu.gd` 的 `_ready()` 补上 `PROCESS_MODE_ALWAYS`，与另三个菜单对齐。

**补充核实**：`loading_screen.finish()` 的 `MOUSE_FILTER` 释放已经在 await 之前，
即历史上"载入遮罩挡住点击"的机制已不存在；主菜单场景内也没有 SubViewport，
不受 ③ 的输入阻断影响。

## 二、门禁自身的假阴性缺陷 —— 已修

**现象**：`bash tests/run_all.sh` 每轮报**不同的**套件失败（framework+floor_flow
→ proj_mgr+floor_flow → proj_mgr），而同样的套件单独跑却通过。

**根因**：套件跑完调 `get_tree().quit(0)`，进程随即退出，**stdout 管道里尚未
冲刷的缓冲被丢掉**——`$(...)` 抓到的流是**被截断的**，截断位置每次不同。
证据：某轮输出第 43 行刚打印 `ALL FLOOR FLOW TESTS PASSED`，第 44 行紧接着
`(未出现 PASSED 标记——脚本可能加载失败或挂起)`。

**修法**：`run_all.sh` 改为**退出码 + 文本标记双判据**（抽出共用 `_judge()`）。
退出码不受缓冲影响，是权威信号；文本标记保留，用于兜住"退出码 0 但实际有
断言失败"的情况。

**验证方式**（遵守"不得为验证工具而覆盖真实文件"）：另建两个临时探针脚本——
一个含故意语法错误（期望判 FAIL）、一个裸 `quit(0)` 且无 PASSED 标记
（期望判 PASS）。两者判定均正确，探针已删。

## 三、`proj_mgr` 间歇性失败 —— 已修（**测试缺陷，非产品 bug**）

**现象**：`test_projectile_manager.tscn` 约 4 次挂 3 次，报
`[FAIL] 投射物对群体单位造成伤害（hp 500 → 500）` 或
`[FAIL] 爆炸波及半径内的群体单位（hp 500 → 500）`。

**排查过程**（逐步排除）：核的 `get_position_buffer` 布局、`_is_crowd_ref` /
`_apply_damage_to_crowd` 守卫、阵营映射、`_sim_manager` 的 `found[0]` 取法
——全部正确。加逐帧诊断后拿到决定性数据：

```
[DIAG] f9  ref=4 crowd id=1 at (6.00,6.00)   # 刚生成，还在测试指定的坐标
[DIAG] f17 ref=4 crowd id=1 at (14.60,15.00) # 一帧内跳到别处
```

**根因**：测试把群体假人刷在**硬编码坐标** `(6,6)` / `(14,14)`，而模拟核每帧跑
`phase_collide_obstacles` —— 单位若落在**墙格**上会被立刻推出墙外（`(14,14)`
那次被推到 `(14.6,15.0)`，位移 0.6）。测试却仍按**生成坐标**发射投射物，
于是弹道从单位旁 0.6 米处擦过，恰好超出命中半径
（`rr = 目标半径 0.35 + 子弹半径 0.30 = 0.65`，只差 0.05 的余量）。
房间布局逐次随机 ⇒ 只有落在墙格的那些轮次失败。

**修法**：测试改为**按单位的实际位置**发射投射物
（`crowd.call("unit_position", id)`），并把落点从 `(6,6)`/`(14,14)`
（在多个房间 JSON 里都是墙）挪到房间内部的原点附近。

**验证**：连续跑 10 次，`pass=10 fail=0`；随后全量门禁连续 3 次 22/22。

## 七、群体单位 / 投射物换掉占位网格（任务清单第二条，本轮完成）

此前群体单位是 `CapsuleMesh`、投射物是 `SphereMesh`，都是占位。本轮改为
**billboard 精灵**，并顺带把两者的渲染统一到一支着色器上。

### 新增

| 文件 | 作用 |
|---|---|
| `rendering/shaders/unit_billboard.gdshader` | 群体单位与投射物**共用**的 MultiMesh 实例着色器 |
| `data/tiles/sprite_defs.gd` | 单位精灵表的唯一真相源（哪一格是哪种单位、按什么规则挑格） |
| `assets/sprites/units_16x16.png` | 烘焙产物：tiny-dungeon 图集底部四行 × 前 5 列（80×64，5 列 × 4 行） |

**为什么两支场景共用一支着色器**：billboard 数学（从实例矩阵取缩放、绕 Y 轴
朝相机、顶点存单位尺寸）**逐字相同**，差别只有两处——群体单位从
`INSTANCE_CUSTOM` 取精灵格采样图集，投射物不采样、颜色走 `COLOR`。
复制成两支会让这段数学有两份真相，而两边的缓冲布局本来就一样
（都恰好开一个实例通道 ⇒ stride 16）。用 `use_instance_color` 一个 bool 分流。

**弹丸不用贴图**：tiny-dungeon 的角色行里没有弹丸类小图，为子弹单独烤一张
1 格贴图不值得。配色复用既有的 `Projectile.element_color()`
（近战/旧投射物路径的唯一真相源），另起一套会立刻产生不一致。

**接触阴影做进着色器**而不是另开阴影实例：MultiMesh 每实例只有一条 transform
+ 一条通道，加阴影要么翻倍实例数、要么每帧在 GDScript 里重算 buffer
（2048 单位下这份开销就吃掉帧预算）。现在是精灵自身下半部按 `smoothstep`
压暗，给俯视相机一个"站在地上"的锚点。

### 踩坑一：MultiMesh 的实例步长（stride）与缓冲长度

**这是本轮最隐蔽的一处**，写下来免得重犯。

- 核产出的渲染缓冲是**每实例 12 个 float**（3×4 变换矩阵）——这是核的契约，
  C++ 侧与降级侧实现一致，不能改。
- 而 MultiMesh **开几个实例通道决定 stride**：只开 `TRANSFORM_3D` 是 12，
  再开**恰好一个**（`use_custom_data` 或 `use_colors`）是 **16**
  （12 变换 + 4 通道，通道落在 float [12..15]），两个都开是 20。
- `multimesh.buffer = <数组>` 是**整段赋值**，长度与 MultiMesh 现有缓冲不符时
  Godot **直接拒收**（`Cannot set a buffer on a Multimesh that is a different
  size from the Multimesh's existing buffer`），**表现是"单位一只都不显示"**
  ——不是报错崩溃，是静默不画。

所以两个管理器的 `_sync_render()` 都必须做一次 **12→16 的重排**，
不能把核的数组直接赋过去。

**这处还连带出了三条门禁失败**（`class_mech` 2 条 + `gameplay` 1 条）：
每帧一条错误日志拖慢了物理循环，恰好打破两个对帧数/计时敏感的用例
（冲刺双击、连击衰减）。排查时**没有预设"是既有 flaky"**——先把两个改动文件
`git stash` 掉跑门禁（22/22 全绿）证明是自己的改动引起，再 `git stash pop` 定位。

### 踩坑二：`use_custom_data` / `use_colors` 必须在 `instance_count` 之前设

设过 `instance_count` 之后再切这两个开关，Godot 报
`Instance count must be 0 to toggle whether custom data is used`。
两个 `_setup_multimesh()` 里的赋值顺序因此不能动，代码里已写注释标明。

### 踩坑三：精灵烘焙抠反了（**已修**）

第一版截图里每只怪都顶着一块**黑方块**。诊断过程：

1. 检查烘焙产物：`alpha 直方图 0:112 / 255:5008` ⇒ 98% 不透明，背景根本没抠掉。
2. 回头读**源图**：它是索引色 PNG（colorType=3），`tRNS` 只有 1 项且值为 0
   ⇒ **只有调色板索引 0 是透明的**，角色外的空白格用的正是索引 0。
3. 而当时被当成"背景色"的 RGB(118,59,54) 是调色板**索引 24**，
   那是角色的**深栗色描边**。

于是第一版按颜色距离抠图**正好抠反**：把描边抠成透明、把真背景留成不透明。
且因为黑方块在深色场景里不显眼，很晚才被发现。

**正确做法**：调色板索引 → RGBA 直接展开（alpha 取 `tRNS[i]` 或 255），
**不做任何颜色阈值判断**。重烘后不透明 3986 / 透明 1134（22.1% 透明），
剪影干净。教训已写进 `sprite_defs.gd` 文件头：
**索引色 PNG 先读 `tRNS` 和 PLTE，不要靠肉眼取色猜背景。**

### 验证

窗口化实跑（`--headless` 下 MultiMesh buffer 回读恒为空、`set_instance_transform`
被丢弃，**stride 问题只能在有窗口模式下复现**）：9–15 只群体单位渲染出三种
不同精灵（村民 / 橙衣壮汉 / 灰狼），7 发元素配色弹丸（火橙 / 冰蓝 / 电黄 /
毒绿 / 土棕 / 风白 / 无元素白）。临时探针与中间产物已全部清理。

## 八、待用户决策（本轮新增）

以下几项**已明确是设计/审美取向问题，不替用户拍板**：

1. **billboard 是否要朝向移动方向**。两侧核的渲染缓冲**都不写旋转**
   （只有对角缩放 + 末列位置），所以单位只能"永远正面朝相机"，无法"朝行进方向"。
   要支持得改 `crowd_sim.cpp` 的 `fill_render_buffer` **和** `crowd_sim_fallback.gd`
   **并重编 DLL**（本机未见 SCons 工具链）。
2. **美术风格落差**。tiny-dungeon 是明亮可爱的地牢包，《噬铁者》是暗色锈铁主题。
   是否调色/换源是审美决定。
3. **范围**：本轮只做了**群体单位 + 投射物**。玩家（`player.tscn` 的
   `CapsuleMesh_player`）与节点式敌人（`enemy_base.gd:_create_visual()` 的
   `CapsuleMesh`）**也还是胶囊**，换它们是大得多的改动（涉及动画状态、
   朝向、受击闪白等一整套表现）。
4. **群体单位动画**。素材每个角色只有**单帧**。要做多帧动画得走
   `custom_data` 传帧号 + `INSTANCE_CUSTOM` 在着色器里换格，
   核不需要改（通道数据本来就有 4 个 float 富余），但需要素材支持。

## 十一、群体路径词缀接入（任务清单第二条，本轮完成）

### 问题

词缀（`AffixDB`，怪物设计分册第 7 章）本来是挂在 `EnemyBase` 节点上的：
数值型由 `AffixDB.apply()` 写进 monster dict，非数值型由
`enemy_base._apply_affix()` 装配战斗钩子。

群体单位**不是场景节点**，两条路都断了。房间生成里 `AffixDB.apply()` 在
swarm/节点分流**之前**就跑了（`room_controller.gd:642`），所以群体单位
拿到了带 `affixes` 的 monster dict，但群体路径**只读了 `speed_pct`**
（生成时读一次），其余全部静默失效：

| 词缀 | 群体路径旧行为 |
| --- | --- |
| fast | 只有 `speed_pct` 泄漏进来，且**根本没写回核**（见下） |
| strong | `atk` 写进 dict 但从不读 |
| burn / freeze / revenge / immortal / lifesteal / void / chaos | 全部失效 |

### 实现

- **新增** `gameplay/enemies/crowd_affix_store.gd`（`CrowdAffixStore`）——
  按单位 id 索引的词缀状态与结算。数值口径逐条对齐 `enemy_base` 的同名常量。
- **新增** `CrowdManager.damage_unit(id, amount, attacker, pos)` ——
  所有"由 GDScript 侧发起的伤害"统一入口。复仇/不朽必须**在扣血之前**介入，
  直接 `apply_damage` 会让这两种词缀失效。调用方已全部迁移：
  `player._apply_hit_crowd`、`projectile_manager._apply_damage_to_crowd`、
  `projectile_manager._explode_crowd`。
- **新增** `CrowdManager._set_unit_speed(id, speed)` —— 核没有 `set_speed`，
  走 despawn + 同位 spawn（LIFO 保证 id 不变）。
- **新增** `CrowdUnitHost.take_damage(amount, is_crit, knockback, from)` ——
  群体单位的节点代理，承接玩家「伤害反弹」词条的回流伤害。
- **新增** `CrowdManager.host_of(id)` —— 暴露宿主节点（`buffs_of` 要穿
  `BuffHolder._target` 私有字段，语义不清）。
- `crowd_attacked` 信号**加 `id` 参数**，`room_controller._on_crowd_attacked`
  据此把攻击者节点补上。

### 过程中发现并修掉的四个真 bug

1. **`force_position` 不存在**。`_apply_on_hit_affixes` 调了
   `_player.call("force_position", ...)`，但全项目只有
   `enemy_base._swap_with_player` 里的 `has_method` 检查提到过这个名字，
   **从未定义**。后果：词缀·虚空把怪瞬移走了、玩家留在原地。
   改为直接写 `global_position`（与 `_swap_with_player` 的 else 分支一致）。

2. **反伤调用签名错**。`note_damage` 用四参
   `attacker.call("take_damage", back, null)`，但生产路径上 `attacker`
   **永远是玩家**，玩家侧是两参 `take_damage(amount, from)`。
   Godot 报 `Cannot convert argument 2 from Nil` 并**静默反伤失败**——
   `enemy_base._reflect_to` 的注释里记着同一个坑。已改两参。

3. **`_atk_interval` 被复位覆盖**。`_apply_spawn_affixes` 里先写
   `_atk_interval` 再调 `_recompute_attack_params()`，而后者在
   `active <= 0` 时会**复位成默认 1.2**。由于该函数在 `active += 1`
   之前调用，**第一个单位生成时必然被覆盖**——表现为"攻击间隔永远是
   默认值，怪物的 `attack_interval` 不生效"。已把写入挪到重算之后。

4. **`fast` 词缀在群体路径上从未生效**。`speed_pct` 只被 `_spawn_crowd_at`
   读去当 spawn 参数，而词缀生效需要**再乘一次**；且核里 `speed` 只在
   spawn 时能写，故必须在交给核之前算好。现在 `spawn_unit` 在 spawn 后
   立刻用 `_set_unit_speed` 写回调整过的速度。

### 有意的范围收缩（非遗漏）

- **混沌**只改移速：核里 `attack_range/interval/damage` 是**全体共用**的
  一组参数，改不了单个单位（节点侧会随机改攻速/移速/攻击力三项）。
  为补偿，群体侧**每次都改移速**，把节点侧三分之一的频率补回来。
  重掷是**围绕生成倍率**做的（不是原地累乘），否则倍率会随时长漂走。
- **燃烧/冰冻**复用玩家侧既有的 `BuffHolder` 词条（`burn` / `frost`），
  与节点侧 `enemy_base` 施加的是同一套。
- **精英标记仍未透传给核**（`sim.set_elite` 从未被调），
  `crowd_died` 的 `is_elite` 恒为 false。影响面小（`_should_use_crowd`
  已把精英挡在群体路径外），故未动。

## 十三、音效接线（本轮完成）

### 问题

`AudioManager.play(name)` 的**整条链路是断的，而且完全静默**：

- `play()` 里写的是 `match name:` —— `name` 是**节点名**（本 autoload 注册为
  `AudioManager`），**不是参数 `_sfx_name`**。四个分支永远进不去。
- 即便进去了，分支指向的 `res://assets/audio/hit.wav` 等四个文件
  **全项目不存在**。
- `play()` 无返回值、不报错、不警告。故 `player.gd` 里四处调用
  （受击 / 击杀 / 拾取 / 死亡）**一声不响**，看起来像"音效还没做"，
  实际是接错了变量名。这正是本项目反复出现的那类缺陷：
  **不崩溃、不报错，只是什么都不发生**。

素材其实一直在：`assets/rpg-audio/`（Kenney「RPG Audio」，CC0）有 107 个
ogg，从未被任何代码引用。

### 修法

- `SFX_MAP` 语义名 → 素材文件（按**听感用途**挑，素材本身没有语义命名）：
  `hit → knifeSlice2`（金属割裂）/ `pickup → handleCoins`（金币哗啦）/
  `death → creak3`（木构呻吟）/ `menu_click → metalClick`。
- `play()` 改为查表 + `play_sfx(SFX_DIR + file)`；未登记的名字**静默返回**
  （音效缺失不该打断游戏逻辑）。
- 新增 `has_sfx(name)` —— 语义名已登记**且素材真实存在**，供测试断言。
- 新增 `connect_buttons(root)` —— 递归给 UI 子树里所有按钮接点击音，
  `is_connected` 保证幂等。**用递归而不是逐个手接**：菜单按钮散落在各处
  的 `@onready` 字段里，逐个补意味着以后每加一个按钮都要记得再补一行，
  而那正是这类"静默无声"缺陷的成因。已接：主菜单 / 暂停菜单 / 设置面板。

**只登记已接线的名字**：初版表里还有 `door` / `chest` 两条，但没有调用点，
等于在表里留死条目——已删。要加就先把调用点接上。

### 验证

`tests/test_framework.gd` 新增 `test_audio_wiring`（6 条断言）：
四个调用点的语义名都能通过 `has_sfx`（即**素材真实存在**）、未登记名安全
返回 false、`connect_buttons` 覆盖**深层**子节点（只扫一层会漏）、重复调用
不叠加连接（叠加会让一次点击放两声）。

## 十五、全项目非纹理资源从未导入（本轮发现并修复）

### 现象

实跑点击菜单时编辑器报错：

```
ERROR: audio_manager.gd:131 @ _load_audio(): Failed loading resource:
       res://assets/rpg-audio/Audio/metalClick.ogg.
```

即第十三节刚接好的音效**仍然是全断的**，只是原因换了一个。

### 根因

**全项目所有非纹理资源的 `.import` 都停留在旧格式**（带 `valid=false`、
无 `path=`/`dest_files=`），Godot 4.7 因此从不导入它们：

| 类型 | 数量 | 状态 |
|---|---|---|
| `.obj` | 76 | `valid=false` |
| `.ogg` | 58 | `valid=false` |
| `.glb` | 30 | `valid=false` |
| `.fbx` | 9 | `valid=false` |
| `.ttf` | 2 | `valid=false` |
| `.png` | 1884 | **正常**（4.7 新格式，无 `valid` 字段） |

对照：正常导入的 PNG 的 `.import` 里**没有 `valid` 这一行**，
而是有 `path="res://.godot/imported/xxx.ctex"` + `dest_files=[...]`。
`valid=false` 是**未导入状态的占位配置**——`ResourceLoader.exists()` 对它
返回 **true**，`load()` 返回 **null**。

**证据链**（逐条排除，不预设结论）：

1. 素材本身正常：PowerShell 解析 ogg 容器 —— `OggS` 版本 0、
   6 个页、首页包签名 `vorbis`、Vorbis 版本 0、解析恰好走到文件末尾。
2. Godot 的解码器正常：`AudioStreamOggVorbis.load_from_buffer(原始字节)`
   **成功**，解出 0.4458 秒真实音频。
3. 只是导入器没跑：`.godot/imported/` 里 5142 条产物**没有一条**是音频
   （只有 `ctex` / `scn` / `fontdata`）。
4. `--import` 与编辑器 `reimport` 都**报告成功却零产出**——它们跳过
   `valid=false` 的条目。
5. **决定性验证**：删掉 `metalClick.ogg.import` 后触发 `scan()`，
   Godot **立刻**生成正确的 4.7 格式 `.import`（含 `path`/`dest_files`）
   并产出 `.oggvorbisstr`；随后 `load()` 成功、长度 0.4458 秒。

### 修法

删除陈旧 `.import` 让编辑器重新生成（**不动素材**）：

- `assets/rpg-audio/Audio/*.ogg.import`（51 个）
- `assets/ui-pack/Sounds/*.ogg.import`（6 个）
- `assets/ui-pack/Font/*.ttf.import`（2 个，文件名含空格，需逐个引号处理）

随后 `filesystem_manage(op="scan")` → 51 个 `.import` 全部重建、
`.godot/imported/` 产出 **58 个 `.oggvorbisstr`**、字体 2 个。

**未处理**：76 obj / 30 glb / 9 fbx —— 全项目**零引用**
（仅 `addons/iron_studio/` 有一行 `.glb` 后缀判断字符串），
按"不扩大改动面"未动。将来要用 3D 模型时，同样删 `.import` + 扫描即可。

### 连带修掉的测试假绿（**重要**）

上一轮 `has_sfx()` 用的是 `ResourceLoader.exists()`，对
"文件在、但没导入"的资源**返回 true**——所以第十三节那 6 条断言
**全是假绿**，而运行时一声不响。这正是本项目反复出现的那类缺陷。

- `has_sfx()` 改为走真实 `_load_audio()`（`load()` 拿不到就是 false）。
- `_load_audio()` 失败时 `push_warning`，不再静默返回 null。

修正后测试**正确地变红**（4 条 `FAIL [AudioWiring]`），
导入修好后才转绿 —— 证明这条断言现在真的守着东西。

### 验证

- `ALL 1368 TESTS PASSED`；门禁 `bash tests/run_all.sh` → **23 套全绿**。
- 实跑点击菜单按钮：`Failed loading resource` 错误**全部消失**。

## 十八、复验「按 E 拾取」（第十七节遗留的疑点，本轮结论：**功能正常，无需修复**）

### 背景

第十七节把「按 E 没反应、也不提示」定为**已修**，根因是像素化提交把 Player
搬进 SubViewport 后 `gui_disable_input = true` 阻断了转发事件。但复验时发现
一个**对不上的现象**：`Player._pickup_field()` 在实跑中返回 `null`，
看起来像"掉落物管理器找不到 ⇒ 拾取链路仍然是断的"。

### 排查（每一步都实测，不预设结论）

1. **输入链路**：探针挂在 `root` 与 SubViewport **两处**同时抓 `_input` /
   `_unhandled_input`，注入 E 键 ⇒ 两处都收到，且**视口内那一份也收到**。
   ⇒ `gui_disable_input` 确实已是 `false`，输入没有被阻断。
2. **action 匹配**：`InputMap.action_get_events("interact")` = `keycode=E`
   （**无修饰键**），合成 `InputEventKey` 的 `event_is_action(ev,"interact")`
   返回 **true**。⇒ 注入事件与绑定是匹配的，不存在"事件到了但不算 interact"。
3. **实跑空手按 E**：`EventBus.message` 收到
   **「附近没有可拾取的掉落物」** ⇒ E 键**确实到达了** `Player._unhandled_input`
   并走进了 `_pickup_nearby()`。
4. **实跑有掉落物按 E**：造一件掉落物后按 E，收到
   **「拾取：铁制单手剑·蓝」**，`nearest` 随即变为 `<null>`。
   ⇒ 拾取**端到端完全正常**。

### 那个 `null` 到底是什么

**不是缺陷**。`PickupField` 由 `LootSystem._field_for()` 在**第一次掉落时**
懒创建，开局房间里根本不存在；`_pickup_field()` 返回 null 时由
`_nearest_pickup()` 的**全量遍历兜底**，链路并未断。
排查中一度把它当成"GameRoot 的 `current_room_node` 指向 SubViewport 外的
残留节点"，并据此改了 `Player._pickup_field()` / `_crowd_manager()` /
`ProjectileManager._crowd_manager()` 三处——**用 A/B 对比（新旧实现并列跑）
证伪**：旧实现同样能拿到正确的 `PickupField`。
原因是 `current_room_node` 存的是**节点引用**而非路径，**子视口边界不影响它**。
故三处改动**已全部撤回**，仅在 `_pickup_field` / `_crowd_manager` 上补了注释，
写明"返回 null 是正常状态"与"引用不跨视口受限"——避免下次重复排查。

### 方法教训（写下来免得重犯）

**"对象为 null" 有两种可能：链路断了，或那一刻它本来就该是 null。**
本次差点因为没区分这两者而给一个**本来正常**的函数动手术。
判据：先确认该对象**在当前状态下是否应该存在**，再判断 null 是否是缺陷。

### 验证

```
bash tests/run_all.sh   →  23 套 / 全部套件通过
```

实跑证据（临时探针，已全部删除）：空手 → 「附近没有可拾取的掉落物」；
有掉落物 → 「拾取：铁制单手剑·蓝」。

## 十九、静默失效缺陷扫查（本轮：恒真断言 + 两处断链）

承接第十八节的方法教训（"对象为 null" 有两种可能），本轮把**同一类缺陷的
另一种形态**系统扫了一遍：**代码在跑、不崩溃、不报错，只是什么都不发生**。

### ① 三条恒真断言（`... or true`）—— 测试假绿

`grep "or true"` 扫出三处，**它们永远为真，等于没测**：

| 文件 | 原断言 | 该断言什么 |
|---|---|---|
| `test_backpack_ui.gd:89` | `_check(...contains("强化 +1") or true, ...)` | 强化后详情面板是否真刷新了强化等级 |
| `test_element_buff.gd:83` | `_check(not ED.ignores_armor(EARTH) or true, ...)` | 土的护甲穿透口径 |
| `test_gameplay_fixes.gd:81` | `_c(gr.current_room_index == idx_before or true, ...)` | 门触发器重入保护 |

**逐条改成真断言**：

1. **详情面板**：补上 `ui._selected = helm` + `ui._refresh_detail()`
   （`_selected` 是可直接赋值的属性），再断言文本含「强化 +1」，失败时打印实际值。
2. **土/风护甲穿透**：`ignores_armor` 按 `damage_type` 判，土是 `mixed`
   ⇒ 返回 **true**（法术部分无视护甲；物理部分不无视那是 `can_crit` 的事）。
   顺带补了风（同为 `mixed`）。**原注释「土为混合（物理+法术）」与实现本就不一致**
   ——这正说明该断言从未被执行过。改完后门禁立刻变红一次，正是它第一次真的在测东西。
3. **门重入保护**：原来断言"房间号不变"，但**房间号会被 `GameRoot` 的全局防抖
   `TRANSITION_COOLDOWN` 兜住**——即使 `_triggered` 重入保护整个失效，断言照样绿。
   改为**数 `door_opened` 的发射次数**：`_triggered` 是唯一的闸，两者互不遮蔽。
   新增「首次触发恰好发 1 次」作为对照，避免"0 次"也误判为通过。

### ② HUD 毒气层数永不显示（真·玩家可见缺陷）

**现象**：第 6 层硫磺毒气**照常扣真伤**（1.5/层/秒），但 HUD 上没有任何数字。

**根因**：`hud.gd:_update_gas_label()` 用 `get_tree().current_scene` 取 GameRoot。
而 `main.tscn` 的根是 `MainScene`（无脚本），**GameRoot 是它的子节点**——
`current_scene.get("floor_mechanic")` 恒为 null，标签每帧被清空。

**这是全项目唯一一处以 `current_scene` 为主路径取 GameRoot 的地方**：
`room_controller.gd:354` / `hidden_wall.gd:150` / `minimap_view.gd:59` 都是
**先走 `game_root` 组**（`game_root.gd:57` 注册），`current_scene` 只作测试场景兜底。

**修法**：HUD 改为同口径——`game_root` 组优先，`current_scene` 按特征属性
（`dungeon_graph`）递归兜底；结果缓存（`_gr_cache`），因为 `_process` 每帧都调。

**可达性已核实**：`_has_gas()` = `floor_num == 6`，`_add_gas(1)` 每 35 秒
（`GAS_INTERVAL`）自动加层，减层走精英击杀 / 开宝箱 / 泉水。
策划文档里没有毒气的规格条目，**它是自洽的已实现机制**，不是半成品。

### ③ 屏幕震动：信号有发射者、零订阅者，且函数本身是坏的

**两处独立断链**：

- `EventBus.screen_shake` 有 2 处 emit（`projectile_manager.gd:298` 投射物命中、
  `projectile.gd:342` 引信爆炸），**零 `.connect`**。
- 唯一能施加震动的 `CameraRig.shake()`（完整 tween 实现）**零调用者**。

**而且 `shake()` 本身是坏的**：`_shake_offset()` 把相机局部位置写成
`Vector3(±x, camera_height ± y, ±z)` —— y 基准是 **20**（`camera_height`），
但 `_setup_camera()` 已把相机局部位置设为 `Vector3.ZERO`（俯视靠 `rotation` 实现）。
一旦被调用，相机会**瞬间弹到 20 米高再掉回来**。正因为从未接线，这个 bug 一直没暴露。

**修法**：

- `shake()` 重写：偏移围绕**零基**，x/z 取随机峰值、y 恒为 0（俯视投影下 y 抖动
  只会改变画面缩放，不是"震"）。保留「偏移加在 Camera3D 而非 rig」的设计
  ——rig 的 position 每帧被跟随逻辑 lerp，直接改它会被对抗。
- 新增 `_connect_screen_shake()`，在 `CameraRig._ready()` 里接上 `EventBus.screen_shake`。
- 新增 `_shake_tween` 字段：重复震动先 `kill()` 上一条，否则两条 tween 互相拉扯。

**注意**：`player.gd:1756` 的 `_screen_shake()` 是**另一条独立且正常**的路径
（直接写相机位置、指数衰减），本轮的修改不影响它。

### 回归测试

`tests/test_gameplay_fixes.gd` 新增 6 条断言守住本轮修复：

- 毒气层数显示到 HUD / 无层数时清空（守着 ②，`current_scene` 取法会立刻变红）
- 相机架下有 Camera3D / CameraRig 已订阅 `screen_shake` / **震动不改变相机高度**
  / 震动结束后相机回到零基（守着 ③，旧 `_shake_offset` 会在第 3 条变红）

## 二十、已核实**不是**缺口的项（本轮扫查结论，避免下次重复排查）

### 死信号（emit 无订阅）——**刻意保留**

除已记录的 `player_died` / `projectile_hit` 外，另核实 9 个信号有发射者、零订阅者：
`damage_dealt` / `player_moved` / `player_attacked` / `player_skill_cast` /
`room_cleared` / `room_exited` / `door_locked` / `item_picked_up` / `item_devoured`。

`EventBus` 的既定职责就是**广播**——发射者不该知道谁在听。删除它们会缩小
以后接成就/统计/音效/教学提示的扩展面，而代价只是每帧一次空派发。
**故判为刻意保留，未动。** 与 `screen_shake` 的区别在于：那个**有明确的意图
（撞击震屏）和一份现成的、可用的实现**，只是没接上——那是断链，这是留白。

### `damage_dealt` 与 `total_damage` 的语义冲突（**待用户决策**）

`GameManager.total_damage`（结算数据里组装，但结算面板**没有展示它**）
有**两条语义不同的写入路径**：

- `enemy_base.gd:1837` —— `gm.total_damage += amount`，在 **`take_damage` 内**，
  是**玩家承受**的伤害（含无来源的毒气真伤）。
- `DamagePipeline.emit_damage_result` —— emit `damage_dealt(null, target, ...)`，
  由 `combat_system.gd:22,46` 调用，是**玩家造成**的伤害；该信号无订阅者。

两者名字相同、语义相反。**哪个是"本局总伤害"是设计问题，不替用户拍板。**
现状：结算面板不展示该项，故不影响任何可见行为。

### 其余扫查项：**无新发现**

- **`WorldEnvironmentManager`（`world/environment/world_environment.gd`）是零引用死类**。
  已核实其 `_ready()` 里的 `PostProcess.apply_hd2d_settings()` **没有信息丢失**：
  `main.tscn` 的 `Environment` sub-resource 是同一份值的快照，且
  `GameRoot._apply_floor_environment()` 每层重写雾色/环境光（含 `ambient_light_energy`）。
  它唯一的独有语义是与 `GameRoot` 的 `0.4 + lum*1.2` 差一个系数（`1.6` vs `1.2`）。
  **属"有争议"范畴，未动**（删/接/对齐三选一，需用户定）。
- **群体路径**（`_should_use_crowd` → `CrowdManager`）确认可达：`monster_db.gd`
  对 `zombie`/`berserker`/`hound` 设了 `swarm: true`。
- **其余 `current_scene` 用法**（`room_controller` / `hidden_wall` / `minimap_view`）
  全部有 `game_root` 组优先，**只有 HUD 一处漂移**（已修）。
- **match-on-wrong-variable** 类：抽查 `room_controller.gd`（`difficulty` /
  `_room_type` / `event_type`）、`enemy_base.gd`（`death_zone`）、
  `settlement_panel.gd`（`reason`）——全部匹配的是**可能出现的值**，无缺陷。
- **无意义返回值**：`preload_all()`（有真实副作用）、`has_sfx()`（测试用）、
  `preload_stats` 系列（测试访问器）——均正当。

## 二十二、测试私有访问迁移到 probe（阶段 6，2026-09-21）

### 目标

阶段 0 建立了 `tests/helpers/probe.gd`（唯一允许触碰下划线私有成员的地方），
但只做了"新写法可用"，**旧写法仍散落在 16 个测试文件里**。本轮把
**133 处**直呼全部迁移过去。

**为什么值得做**：重构搬走一个私有方法时，直呼它的测试会全部报错——
不是行为变了，是名字挪了位置。于是"重构"变成"重写测试"，而重写过的断言
是照着新实现写的，**测不出行为漂移**。迁移后搬方法只需改 probe 一个文件。

### 迁移范围与手法

| 形态 | 处理 |
|---|---|
| `.call("_xxx", ...)` | → `probe.xxx(host, ...)` |
| `host._xxx`（读字段） | → `probe.xxx(host)` |
| `host._xxx = v`（写字段） | → `probe.set_xxx(host, v)` 或 `probe.set_field(host, "_xxx", v)` |
| `host._xxx(...)`（直接调方法） | → `probe.xxx(host, ...)` |

**新增 11 个访问器**（迁移中发现的覆盖缺口）：`apply_form_modifiers` /
`hit_enemies_in_cone` / `apply_pierce_line_at` / `deal_bonus_damage_crowd` /
`apply_lifesteal` / `apply_on_hit_affixes` / `damage_numbers_enabled` /
`create_elite_marker` / `perform_attack` / `tick_chaos` / 门触发器回调。
probe 访问器总数 **122 → 132**。

### 迁移中修掉的三处真实缺陷

1. **`ctrl_is_special_room` 把方法当字段读**（**probe 自身的 bug**）：
   实现是 `ctrl.get("_is_special_room")`，但 `_is_special_room` 是**方法**，
   `get()` 静默返回 null → false。表现是 room_flow 的 4 条
   「识别为特殊房」全部失败，**看起来像功能坏了，实为探针写错**。
   已改为 `call()` 并加注释警示。
   > 这正是本项目反复出现的缺陷形态：`get()` 拿不到东西时返回 null 而不报错。

2. **`test_gameplay_fixes` 的穿门落点断言只试南北两向**：
   地牢随机生成，起始房未必有南北邻接房 → **间歇性失败**（与代码无关）。
   已改为四向都试，并补上东西向的落点断言。

3. **`probe.spawn_slash_visual` 缺 color 参数**：原调用是四参
   （reach/half_angle/color），probe 只封了三个，迁移后编译报
   "Too many arguments"。已补默认参数。
